## 1. 这是什么

一句话：**它是社区的"门禁 + 电表"，不是模型本身。**

所有成员不再直接拿 Bifrost 的密钥，而是先向网关要一把自己的 key。网关负责两件事：

1. **门禁**：你是不是这个 Discord 服务器的人？不是就进不来。
2. **额度**：全站每小时能用多少 token？超了就拒绝。

请求最终仍然打到老大那台 Oracle 大阪机器上的 Bifrost，由它决定路由到哪个上游。

### 1.1 完整链路

```
社区成员
   │  ① 浏览器点「Discord 登录」
   ▼
┌────────────────────────────────┐
│  本网关（Docker，只监听 127.0.0.1）│
│  · Discord OAuth 门禁            │
│  · 两个全站共享的小时级 token 池  │
│  · 全站每分钟请求上限             │
│  · 令牌（sk-xxx）管理            │
└────────────────────────────────┘
   │  ② 用成员自己的 key 调用 /v1/chat/completions
   ▼
  Bifrost（Oracle 大阪，OpenAI 兼容）
   │  ③ 按模型名路由
   ├──► Z.ai          → glm-5.3-flash
   ├──► OpenRouter    → minimax-m3 / minimax-m3.1-flash
   └──► 本地 AI MAX   → qwen3-embedding / qwen3-reranker
```

> 网关和 Bifrost 通常在同一台机器上。那样上游地址填 `http://127.0.0.1:<Bifrost端口>` 即可，流量不出网卡，不经过 Cloudflare Tunnel。

### 1.2 边界：网关管什么，不管什么

| 事项 | 归谁 |
|---|---|
| 谁能用（Discord 成员校验） | ✅ 网关 |
| 全站每小时能用多少 token | ✅ 网关 |
| 全站每分钟最多调用几次 | ✅ 网关 |
| 发 key、吊销 key | ✅ 网关 |
| 用量明细、审计日志 | ✅ 网关 |
| 调哪个上游、用哪个密钥 | ❌ Bifrost |
| 模型路由、失败重试、负载均衡 | ❌ Bifrost |
| 上游预算与计费 | ❌ Bifrost / 各 provider |

**为什么要多这一层**：如果直接把 Bifrost 的 key 发给大家，你无法知道谁用了多少、也没法在某人滥用时单独停掉他——只能换 key，然后通知所有人重配。网关把这把 key 留在服务器上，每个人拿到的是自己的。

### 1.3 使用规范（必读）

本站是社区公益资源，**不是公共 API 服务**。以下两条是硬规则，不是建议。

#### 规则一：密钥必须按「软件 + 用途」命名

创建 key 时，名字必须让人一眼看出**你用什么软件**、**用来干什么**：

| ✅ 合格 | ❌ 不合格 |
|---|---|
| `cherry-studio-个人笔记问答` | `test` |
| `cline-项目代码补全` | `123` |
| `obsidian-知识库向量检索` | `a` |
| `dify-内部文档机器人` | `我的key` |
| `python-论文摘要脚本` | `sk` |

管理员会按名字核查用途。**看不出用途的 key 会被直接删除**，不另行通知。

#### 规则二：禁止任何形式的商业化使用

包括但不限于：

- 出售、转售、出租本站 API 或额度
- 接入商业平台、商业项目、付费项目
- 作为第三方盈利服务的一部分调用
- 账号共享、账号代用、一人多号占用资源

本站额度是**全站共享**的，一个人拿去变现，等于把所有人的额度都吃掉。

#### 后果

违反上述任一条：**删除相关 key → 停用账号 → 必要时封禁 Discord 身份**。因为是公益资源，处理不会提前警告。

> 拿不准自己的用法算不算商业化，先在社区里问一声，别先跑起来再说。

## 2. 名词表

| 名词 | 含义 |
|---|---|
| **Bifrost** | 老大自建的上游网关，跑在 Oracle 大阪机房，对外是 `https://<域名>` |
| **渠道（Channel）** | 网关里"往哪转发"的配置。本站只有一个渠道，指向 Bifrost |
| **令牌（API Key）** | 你自己的一把 `sk-` 开头的密钥，调用时放在 `Authorization` 头里 |
| **额度池（Pool）** | 全站共享的每小时 token 预算。本站有两个：MiniMax 池、GLM 池 |
| **套餐（Plan）** | 一组额度配置。改套餐 = 改两个池的每小时上限 |
| **全站共享** | 额度不是按人分的。所有人加起来用同一个池，池满则所有人一起等重置 |
| **门禁（Gate）** | 登录时校验你是不是 Discord 服务器成员 |

> ⚠️ 本站**不按美元计费**，也没有充值。额度单位是 **token**，口径是「输入 + 输出合计」，跟上游返回的 `usage.total_tokens` 一致。

## 3. 五分钟上手

假设站点地址是 `https://<域名>`（以实际部署为准）。

### 第 1 步：登录

浏览器打开站点首页，点 **「使用 Discord 继续」**，在 Discord 授权页点「授权」。

授权页会写明网关只能看到：你的账号基本信息、你加入了哪些服务器、你在本服务器里的身份组。**看不到你的消息，也不能替你发消息。**

### 第 2 步：看自己的额度

登录后打开左侧 **个人 → 我的额度**，上面是上下两个框：

```
┌──────────────────────────────────────────────┐
│  MiniMax 用量        minimax 系列模型   已用 3% │
│  29.1M  tokens 剩余 / 每小时                   │
│  ██░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░           │
│  0.9M / 30.0M              47 分后重置        │
└──────────────────────────────────────────────┘
┌──────────────────────────────────────────────┐
│  GLM 用量            glm 系列单独计量   已用 0% │
│  3.0M  tokens 剩余 / 每小时                    │
│  ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░           │
│  0 / 3.0M               首次调用后开始计时      │
└──────────────────────────────────────────────┘
其他模型（如 qwen3-embedding、qwen3-reranker）由社区自有算力提供，免费且不占用上述额度。
```

两个框是**两个独立的池**，互不影响：MiniMax 用光了，GLM 还能继续用。

### 第 3 步：创建令牌

左侧菜单 **常规 → API 密钥 → 新建**。

**名字必须写成「软件 + 用途」**，例如 `cherry-studio-个人笔记问答`、`cline-项目代码补全`。不要用 `test`、`123`、`我的key`——看不出用途的 key 会被管理员删掉（见 [1.3 使用规范](#13-使用规范必读)）。

其余字段留空即可。

> ⚠️ 完整密钥**只在创建成功那一刻显示一次**。页面关掉就再也看不到，只能重新建一个。请立刻复制保存。

### 第 4 步：调用

```bash
curl https://<域名>/v1/chat/completions \
  -H "Authorization: Bearer sk-你的密钥" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "Z.ai/glm-5.3-flash",
    "messages": [{"role": "user", "content": "你好"}]
  }'
```

看到 `"choices"` 就通了。

## 4. 普通成员手册

### 4.1 登录

**唯一入口是 Discord。** 本站关闭了密码注册和密码登录，因为账号体系完全依附于社区身份。

如果你**不在**这个 Discord 服务器里，授权后会回到登录页并看到红色提示：

> **无法登录：不在社区服务器内**
> 仅限本社区 Discord 成员使用，你的账号不在该服务器内。

这是预期行为，不是故障。加入服务器后再试即可。

> 管理员应急入口：`https://<域名>/sign-in?admin=1`，只有管理员账号能用密码登录。普通成员打开这个地址也登不进去。

### 4.2 额度是怎么算的

#### 两个池，全站共享

| 池 | 管哪些模型 | 默认每小时上限 |
|---|---|---|
| MiniMax 池 | `minimax` 系列 | **30,000,000 tokens（30M）** |
| GLM 池 | `glm` 系列 | **3,000,000 tokens（3M）** |
| （不计量） | 其余全部，如 qwen3-embedding / qwen3-reranker | 免费，不占额度 |

三个要点：

1. **全站共享，不是每人一份。** 30M 是所有人加起来一小时的总量。别人用得多，你能用的就少。
2. **口径是输入 + 输出合计。** 一次请求的 prompt 和 completion 都算进去。
3. **两个池互相独立。** GLM 池单独 3M，是因为 GLM 的上游配额更紧；MiniMax 池用尽不影响 GLM。

> 为什么 GLM 单独拆出来：GLM 走的是 Z.ai 的付费额度，而 MiniMax 走 OpenRouter。混在一个池里，跑量的模型会把贵的那个挤死。

#### 计时从"该池第一次被用"开始，不是整点

这是最容易误解的一点：

- 池里还没人用过 → 显示「**首次调用后开始计时**」，没有重置时间。
- 有人发起了第一个请求 → 该池从**那一刻**开始计时，1 小时后归零。
- 归零后 → 下一次有人调用时**重新开始计时**，而不是固定在每小时整点重置。

所以"重置时间"是一个滚动的时间点，跟着实际使用走。

#### 用完了会看到什么

```json
{
  "error": {
    "message": "MiniMax全站额度已用完（已用 30.00M tokens / 上限 30.00M tokens），将于 2026-11-04 09:12:33 重置",
    "type": "new_api_error"
  }
}
```

`message` 里会写明是哪个池、已经用了多少、什么时候恢复。**这是全站状态，不是你个人的问题**——别人也在用同一个池。

#### 还有一道全站限流

除了小时额度，网关还有**全站每分钟最多 30 次调用**的硬闸（可配置）。触发时返回：

```
You have reached the request limit: maximum 30 requests in 1 minutes
```

这道闸跟 token 无关，纯粹防止有人写死循环把上游打爆。遇到就等一分钟，或降低并发。

### 4.3 我的套餐页

左侧 **个人 → 我的额度**。这里显示：

- 套餐名称与生效状态
- 两个池各自的剩余量、已用量、百分比
- 池是否已开始计时、还有多久重置

页面每 30 秒自动刷新一次。

### 4.4 令牌（API Key）管理

路径：**常规 → API 密钥**

创建时可以设置：

| 字段 | 建议 |
|---|---|
| 名称 | **强制**：`软件 + 用途`，如 `cherry-studio-个人笔记问答`。看不出用途会被删 |
| 额度 | 留空 = 不限（**仍受全站额度池与限流约束**）。填了则这把 key 自己也有一个上限 |
| 过期时间 | 长期用就留空；临时分享给朋友一定要设 |
| 模型限制 | 只想让它用 glm，就填 `Z.ai/glm-5.3-flash` |
| IP 限制 | 有固定出口 IP 时填上，能防 key 泄漏被异地使用 |

**多把 key 的好处**：笔记本一把、服务器一把。哪把泄漏了单独删掉，不影响其他。

> 但**不要把 key 借给别人**。账号共享属于违规行为，见 [1.3 使用规范](#13-使用规范必读)。

### 4.5 调用方式

#### 基本信息

| 项 | 值 |
|---|---|
| Base URL | `https://<域名>/v1` |
| 认证 | `Authorization: Bearer sk-xxx` |
| 协议 | OpenAI 兼容（`/chat/completions`、`/embeddings`、`/rerank`、`/models`） |

#### 可用模型

| 模型 ID | 类型 | 计量 | 说明 |
|---|---|---|---|
| `Z.ai/glm-5.3-flash` | 对话 | GLM 池 | 智谱 GLM，快 |
| `openrouter/minimax/minimax-m3` | 对话（多模态） | MiniMax 池 | 支持图片/视频输入，1M 上下文 |
| `openrouter/minimax/minimax-m3.1-flash` | 对话 | MiniMax 池 | MiniMax 轻量版 |
| `Local_Bifrost/AI_MAX/qwen3-embedding` | 向量化 | **免费** | 4096 维，用于 RAG |
| `Local_Bifrost/AI_MAX/qwen3-reranker` | 重排 | **免费** | 检索结果精排 |

> 模型 ID 必须**一字不差**，包括大小写和斜杠。写错会返回 `503 model_not_found`。

#### curl

```bash
curl https://<域名>/v1/chat/completions \
  -H "Authorization: Bearer $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "Z.ai/glm-5.3-flash",
    "messages": [
      {"role": "system", "content": "你是一个简洁的助手"},
      {"role": "user", "content": "用一句话解释什么是向量数据库"}
    ],
    "temperature": 0.7
  }'
```

#### Python（OpenAI 官方 SDK）

```python
from openai import OpenAI

client = OpenAI(
    base_url="https://<域名>/v1",
    api_key="sk-你的密钥",
)

resp = client.chat.completions.create(
    model="Z.ai/glm-5.3-flash",
    messages=[{"role": "user", "content": "你好"}],
)
print(resp.choices[0].message.content)
```

#### Node.js

```javascript
import OpenAI from 'openai'

const client = new OpenAI({
  baseURL: 'https://<域名>/v1',
  apiKey: process.env.API_KEY,

const resp = await client.chat.completions.create({
  model: 'Z.ai/glm-5.3-flash',

```

#### 向量化（RAG 场景）

```python
resp = client.embeddings.create(
```

#### 第三方客户端

凡是支持「自定义 OpenAI 兼容接口」的客户端都能接：

| 客户端 | 填法 |
|---|---|
| **Cherry Studio** | 设置 → 模型服务 → 添加 → 类型选 OpenAI → API 地址 `https://<域名>/v1`，密钥填 `sk-xxx`，模型手动添加上面的 ID |

### 4.6 报错对照表

| HTTP | 错误码 / 文案 | 意思 | 怎么办 |
|---|---|---|---|
| 401 | `invalid_api_key` | key 不对或已被删 | 检查是否复制完整、有没有多余空格 |
| 401 | `token expired` | key 过期了 | 重新建一把 |
| 403 | `该令牌无权使用模型` | key 设了模型白名单 | 换模型，或让管理员改 key 设置 |
| 429 | `request limit: maximum N requests` | 全站每分钟调用次数到顶 | 等一分钟，或降低并发 |
| 429 | `…全站额度已用完…` | 对应的池这一小时满了 | 等重置时间；急用可换另一个池的模型 |
| 500 | `cannot reach xxx (connection refused)` | 上游连不上 | 不是你的问题，找运维 |
| 503 | `model_not_found` | 模型名写错 | 对照上面的表逐字检查 |
| 503 | `no available channel` | 网关里没有能服务这个模型的渠道 | 找管理员 |

## 5. 管理员手册

### 5.1 后台入口

```
https://<域名>/sign-in?admin=1
```

`?admin=1` 这个参数不能省——普通登录页只有 Discord 按钮，只有带这个参数才会显示密码表单。

### 5.2 套餐与额度池

路径：**个人 → 我的额度 → 套餐管理**（管理员登录后可见）

可改的是两个数字：

| 字段 | 说明 | 默认 |
|---|---|---|
| `window_1h_tokens` | MiniMax 池，每小时全站 token 上限 | `30000000`（30M） |
| `glm_1h_tokens` | GLM 池，每小时全站 token 上限 | `3000000`（3M） |

输入框下面会实时换算成 `30.0M tokens` 这样的可读形式。

**填 0 表示该池不限。** 两个都填 0 = 完全不限，退化成普通的 key 分发。

常见配置参考：

| 场景 | MiniMax 池 | GLM 池 | 说明 |
|---|---|---|---|
| 保守 | 10,000,000 | 1,000,000 | 十几个活跃用户 |
| 默认 | 30,000,000 | 3,000,000 | 老大的现行规则 |
| 宽松 | 50,000,000 | 5,000,000 | 活动期放开 |

> **改动即时生效**，不用重启、不用重新登录。用户刷新页面就能看到新上限。
> 改小上限时，已经超标的用户下一次请求会立刻被拒。

**「Clear window usage」按钮**：把两个池的已用量清零，并把计时重置。常用于活动开始前"重新开始一小时的额度"。

**哪些模型进哪个池**：网关按模型名判断——名字里含 `minimax` 进 MiniMax 池，含 `glm` 进 GLM 池，其余**免费、不计量**。所以新加一个本地模型不用改任何配置。

### 5.3 用户管理

路径：**Admin → Users**

| 操作 | 说明 |
|---|---|
| 搜索 | 按用户名或 Discord ID 找 |
| 封禁 | 封禁后该用户所有 key 立即失效 |
| 改额度 | 可单独给某人加余额（与全站池无关，属于另一层限制） |
| 查看用量 | 跳转到该用户的日志 |

> 新用户第一次 Discord 登录时会自动创建账号并**自动发放默认套餐**，不需要手动点。
> 注意：**封人不会释放池里的用量**，因为那是全站共享的账，不是他个人的。

### 5.4 渠道管理

路径：**Admin → Channels**

本站只有一个渠道，指向 Bifrost：

| 字段 | 值 |
|---|---|
| 名称 | `bifrost` |
| 类型 | OpenAI |
| Base URL | `http://127.0.0.1:8080`（同机）或 `https://<域名>`（异地），**都不带 `/v1`** |
| 密钥 | `sk-bf-xxx` |
| 模型 | 5 个模型，逗号分隔 |

**要加新模型**：编辑渠道 → 在模型那一栏末尾追加 `,新模型ID` → 保存。立即生效。

> **尽量不要点「测试」**。每点一次，网关都会真的向上游发一次请求——消耗真实额度、占用全站每分钟调用次数，而且会往日志里写一条无关记录。只在刚改完配置、确实怀疑不通时点一次即可；日常验证用成员的一次真实调用更准。

> Base URL 误填成 `https://<域名>/v1` 会导致实际请求打到 `/v1/v1/chat/completions`，表现为 404。

> **同机部署的坑**：网关跑在容器里，`127.0.0.1` 指的是容器自己。向导会自动把 `127.0.0.1` 改写成 `host.docker.internal` 再写进渠道（compose 里已配 `extra_hosts`）。如果手工在后台填，请直接填 `http://host.docker.internal:<Bifrost端口>`。

> **新模型不用配价格**：网关已开启"自用模式"，未定价的模型按兜底倍率放行。模型目录由 Bifrost 负责，这里只关心 token 额度。

### 5.5 Discord 门禁

路径：**Admin → System Settings → 认证 → Discord**

| 字段 | 必填 | 说明 |
|---|---|---|
| Client ID | ✅ | Discord 开发者后台 → OAuth2 |
| Client Secret | ✅ | 同上，注意别泄漏 |
| 启用 | ✅ | 关掉后整个 Discord 登录消失 |
| **服务器 ID** | ✅ | 就是 `<服务器 ID>`。**留空 = 不做门禁，谁都能进** |
| 身份组 ID | ❌ | 留空 = 只要是成员就放行（当前策略） |
| 邀请链接 | ❌ | 留空 = 被拒时只提示"不是成员"，不给邀请入口（当前策略） |

**怎么确认服务器 ID 填对了**：让一个成员登录，看容器日志：

```
[OAuth-Discord] gate: user=123456789 guild=<服务器 ID> roles=[...] required=[] cached=false
```

`guild=` 后面就是实际校验的服务器 ID。如果这行日志里是别的值，说明填错了。

**以后想收紧成"只有某个身份组能进"**：把身份组 ID 填进去，不用改代码、不用重新构建。身份组 ID 从上面那行日志的 `roles=[...]` 里抄。

### 5.6 日志

| 想看什么 | 去哪 |
|---|---|
| 谁在什么时候用了多少 | **Admin → Usage Logs** |
| 管理员操作审计 | **Admin → Audit Logs** |
| 登录失败原因 | 容器日志 `docker compose logs -f \| grep gate` |
| 上游报错 | 容器日志 `docker compose logs -f \| grep -i upstream` |

## 6. 运维手册

### 6.1 部署

完整步骤见 `deploy/README.md`。最短路径：

```bash
tar -xzf community-gateway-YYYYMMDD.tar.gz
cd community-gateway-YYYYMMDD
bash deploy.sh          # 6 步向导
```

向导会自动识别 CPU 架构（x86_64 / ARM），不需要手动选二进制。

**部署前只需要准备两样东西**：Docker，和一个 HTTPS 域名。

```bash
# Docker Engine + Compose v2（Debian / Ubuntu）
curl -fsSL https://get.docker.com | sh
docker compose version        # 必须能输出版本号
```

服务器要求很轻：1 核 1GB、2GB 空闲磁盘即可（实测容器常驻内存 34MB，镜像 311MB）。
端口 3000 要空着，但**不用对外开放**——只绑 `127.0.0.1`。

不用装 Go / Node / MySQL / Redis / nginx，也不用申请 TLS 证书。

另外两件非软件的事：

- **Discord 应用**：去 <https://discord.com/developers/applications> 新建一个，拿 Client ID / Secret，
  并把 `https://<站点地址>/oauth/discord` 加进 Redirects。
- **网络**：构建镜像时要能访问 Docker Hub 与 Debian 源；运行时容器要能访问 `discord.com:443`。

向导会问的几个关键值：

| 问题 | 说明 |
|---|---|
| 站点地址 | 成员浏览器访问的地址，必须和 Discord 回调一致 |
| Discord 应用 | Client ID / Secret |
| Discord 服务器 ID | 留空 = 不做门禁 |
| 管理员账密 | 首次初始化 + `/sign-in?admin=1` 用 |
| Bifrost 根地址 | 同机填 `http://127.0.0.1:<端口>`；不带 `/v1` |
| Bifrost 密钥 | `sk-bf-xxx` |
| 对外暴露的模型名 | 逗号分隔，必须和上游一致 |
| 全站每分钟调用次数 | 默认 30，0 = 不限 |

### 6.2 反向代理

网关只监听 `127.0.0.1:3000`，**不能直接暴露到公网**。用 Cloudflare Tunnel / Caddy / nginx 把 HTTPS 转进来。

Cloudflare Tunnel 的配置片段（`config.yml`）：

```yaml
ingress:
  - hostname: ai.<域名>            # 网关自己的子域，不要占用 Bifrost 的
    service: http://127.0.0.1:3000
  - hostname: <域名>               # Bifrost 原有的，保持不动
    service: http://127.0.0.1:8080
  - service: http_status:404
```

> 两个服务同一台机器时，**加一条 ingress 就够了**，不需要新买域名、也不需要动 Bifrost 那条。

### 6.3 备份与恢复

数据全在 Docker 命名卷 `community-gateway-data` 里，就是一个 SQLite 文件。

**备份**：

```bash
docker run --rm \
  -v community-gateway-data:/data:ro \
  -v "$PWD:/backup" \
  alpine tar czf /backup/gateway-$(date +%F).tar.gz -C /data .
```

**恢复**：

```bash
docker compose down
docker run --rm -v community-gateway-data:/data -v "$PWD:/backup" \
  alpine sh -c "rm -rf /data/* && tar xzf /backup/gateway-2026-11-04.tar.gz -C /data"
docker compose up -d
```

> 备份时容器可以继续跑（WAL 模式下拷贝是安全的），但最稳妥还是先 `docker compose stop`。

### 6.4 升级

二进制在镜像里，换二进制 = 换镜像：

```bash
docker compose down
cp /path/to/new/new-api bin/new-api
docker compose up -d --build
```

数据库结构会自动迁移（AutoMigrate），不需要手动跑 SQL。**升级前先备份。**

> 从旧版（三窗口 / 美元口径）升级上来时，旧字段 `window_5h_quota` 等会留在表里但不再使用，不影响运行；`window_1h_tokens` / `glm_1h_tokens` 会自动补上，默认 0（不限）。**升级后请去后台把两个池的值填回 30M / 3M。**

### 6.5 监控

```bash
# 容器是否健康
docker ps --filter name=community-gateway

# 健康检查端点
curl -s http://127.0.0.1:3000/api/status | head -c 100

# 最近的错误
docker compose logs --since 1h | grep -E "ERROR|error"
```

建议加一条外部监控，每 5 分钟打一次 `https://<域名>/api/status`，非 200 就告警。

### 6.6 换域名

1. 改反向代理 / Cloudflare Tunnel 指向新域名
2. 后台 **System Settings → 通用 → 服务器地址** 改成新地址
3. Discord 开发者后台 → OAuth2 → Redirects 改成 `https://新域名/oauth/discord`
4. 重新登录一次验证

> 第 2、3 步必须一致，否则 Discord 授权回来会报 `redirect_uri` 不匹配。

## 7. 故障排查

### 登录相关

| 症状 | 原因 | 处理 |
|---|---|---|
| 点登录后白屏 | 回调地址和 Discord 里填的不一致 | 对比后台的服务器地址与 Discord Redirects |
| 报 `invalid_client` | Client ID / Secret 填错 | 重新复制，注意 Secret 只需填一次 |
| 报 `仅限本社区 Discord 成员使用` | 账号不在服务器里 | 确认已加入，且服务器 ID 填的是 `<服务器 ID>` |
| 成员也被拒 | 服务器 ID 填错 | 看日志 `guild=` 后面的值 |
| 一直跳回登录页 | Cookie 被拦 | 确认走的是 HTTPS，且浏览器没禁第三方 Cookie |

### 额度相关

| 症状 | 原因 | 处理 |
|---|---|---|
| 两个框都显示「不限」和 ∞ | 套餐里填了 0 | 去「套餐管理」填回 30000000 / 3000000 |
| 刚部署就"额度已用完" | 上限填成了很小的值，或被前一次测试的用量占满 | 点「Clear window usage」后确认上限 |
| 改了上限但页面没变 | 浏览器缓存 | 强制刷新（页面本身 30 秒自动刷新） |
| 额度没超但被拒 | 可能是全站每分钟限流 | 看 message 是「额度已用完」还是「request limit」 |
| 已用量一直不归零 | 窗口从该池首次使用起算，不是整点 | 看「重置时间」那一栏 |
| 本地 embedding 被拒 | 不该发生：它免费且不计量 | 检查模型名里是否误含 `minimax` / `glm` |

### 上游相关

| 症状 | 原因 | 处理 |
|---|---|---|
| 503 `model_not_found` | 模型名不在渠道的模型列表里 | 渠道里补上，或检查拼写 |
| 401 `invalid_api_key` | Bifrost 的 key 失效 | 更新渠道密钥 |
| 500 `cannot reach xxx` | Bifrost 挂了或网络不通 | 上 Oracle 机器看 Bifrost 状态 |
| 502 / 504 | Cloudflare 超时（默认 100 秒） | 长请求改用流式，或调大超时 |
| 同机却连不上 `127.0.0.1` | 容器内的 127.0.0.1 是容器自己 | 改用 `host.docker.internal` 或 `172.17.0.1` |

### 系统相关

| 症状 | 原因 | 处理 |
|---|---|---|
| 容器起不来 | 端口被占用 | `docker ps` 看谁占了 3000 |
| 大量 500 `database is locked` | SQLite 并发写冲突 | 见下方说明 |
| 磁盘满 | 日志没轮转 | compose 已限制单文件 20MB × 5 |

> **关于 `database is locked`**：SQLite 是单写者模型。本站已经开了 WAL + 10 秒 busy_timeout + 连接池上限 8，正常情况下不会出现。如果频繁出现（比如每分钟都有），说明并发写超过 SQLite 的承受能力，应该换 MySQL 或 PostgreSQL。

## 8. 安全清单

部署完请逐条确认：

- [ ] 端口只绑 `127.0.0.1`，公网只能通过 HTTPS 入口进来
- [ ] `.env` 权限 600，且不在版本库里
- [ ] `SESSION_SECRET` 是随机生成的（向导会自动生成）
- [ ] 管理员密码不是默认值
- [ ] Discord Client Secret 没有出现在任何聊天记录、截图、文档里
- [ ] Bifrost 的 `sk-bf-*` 只存在于网关数据库，没有发给普通成员

- [ ] 定期检查 **Admin → Users** 有没有异常账号
- [ ] 定期扫 **常规 → API 密钥**：名字不是「软件 + 用途」格式的，按 [1.3](#13-使用规范必读) 删掉

## 9. 附录

### 9.1 token 量级速查

| 用量 | 大约等于 |
|---|---|
| 1,000 tokens | 一篇 700 字中文短文 |
| 10,000 tokens | 一次长文档问答（含上下文） |
| 100,000 tokens | 读完一本 200 页的书再提问 |
| 1,000,000 tokens | 约 700 万汉字，日常聊天够一个人用很久 |
| 30,000,000 tokens | 默认 MiniMax 池的一小时总量 |

> 真实消耗取决于输入输出比例。**长上下文对话最费**——每一轮都要重发全部历史，第二轮就是前一轮的两倍。
